# The on-disk report format

The contract between whoever **writes** the review (`bazel-review-fleet` and the three lenses) and
whoever **publishes** it (`bazel-post-report`). Both sides read this file, and it is the **only**
source of the format: no report structure lives in the `SKILL.md` files.

The report is readable markdown — you open it in an editor and read it. What makes it
publishable are HTML metadata comments: invisible in GitHub's render and in the editor, and
it is from them that `bazel-post-report` takes `path`, `line` and severity to anchor each inline
comment. Without them the publisher cannot anchor anything and falls back to a single comment
on the PR body.

## This document is normative

Everything here is mandatory, and one rule outranks all the others:

> **Nothing that is not specified here goes into the file.** No extra section, no extra
> label, no extra summary line, no emoji, no table of contents, no "generated by". When
> there is no field for something a lens returned, it goes away — it does not become a new
> section.

The report is not the place to exercise style. It is read by a parser (`bazel-post-report`) and
compared across runs; a stable format is what makes two runs on the same PR diffable and what
lets the publisher detect a duplicate.

Validate before you hand it over:

```bash
bash .claude/skills/bazel-review-fleet/references/validate-report.sh .reviews/pr-123.md
```

## Where the report goes

Under Bazel the report is **the agent's final output**: Bazel saves it under its reviews
directory with its own header on top, shows it on its page, and hands that saved file to
`bazel-post-report` when you publish. See `headless.md`, section 3.

The skill validates it from a scratch file outside the clone (`headless.md`, section 3) and
never writes inside the clone.

**The report carries no memory of previous runs**, and that is deliberate — it is a statement
about one diff at one sha, not a ledger. Decisions the team took on earlier findings live on the PR, in resolved threads and
replies, and `bazel-post-report` is what reads them back.

Every path the PR changes is part of the change set, `.claude/` included (`headless.md`,
section 2). A review makes no write to the working tree at all: it never applies a fix, never
commits and never pushes.

## Closed vocabularies

Three lists. A value outside them is an invalid report — do not invent, do not abbreviate, do
not translate, do not create a variant with a space in it.

### `severity`

`critical` · `major` · `minor` · `nit`

All three lenses **already emit this scale** in their JSON. Copy `severity` verbatim from the
lens's field into the finding's attribute: **there is no conversion at write time.** If a lens
returns `warning`, `high`, `medium` or `low`, it is out of date with its own contract — ask
for the JSON again instead of converting by hand, because improvised conversion is exactly
what made two reports on the same diff come out different.

A `lazy-senior-dev` cut is **never** `critical`: a simplification does not block a merge.

### `class`

One dimension per finding, always kebab-case, always without a space (so never quoted):

| Group | Values |
|---|---|
| Security | `injection` `authz` `validation` `secrets` `crypto` `web3` |
| Correctness | `logic` `error-handling` `regression` `test-gap` `test-validity` `assumption` |
| Runtime | `perf` `resource` |
| Structure | `architecture` `quality` `migration` `idiom` `deps` |
| Surface | `a11y` `docs` `hygiene` `pr-mismatch` |
| Subtraction | `delete` `reuse` `stdlib` `native` `drop-dep` `yagni` `shrink` `out-of-scope` |

The value arrives ready from the lenses: `exploit-digger` emits `class`, `lazy-senior-dev`
emits `tag` (which **is** the class, from the Subtraction group) and `senior-code-reviewer`
emits `class` alongside its A–K `dimension`. The `dimension` letter **never** goes into the
`class` attribute.

`deps` is a dependency with a problem (CVE, version); `drop-dep` is a dependency that should
go away.

### `verdict`

`request_changes` · `comment` · `approve`

It goes in the header and in the summary line. It never becomes a GitHub review `event` —
that is a `bazel-post-report` rule.

## The header block

The first thing in the file, **line 1**, before any prose. One key per line, `key: value`, in
this order, with no blank line in between:

```markdown
<!-- review-fleet:v1
repo: owner/name
pr: 123
base: develop
head_sha: a1b2c3d4e5f67890abcdef1234567890abcdef12
scope_cmd: git diff origin/develop...HEAD
files: 12
lenses_ran: senior-code-reviewer, exploit-digger, lazy-senior-dev
lenses_skipped: none
verdict: request_changes
-->
```

The marker is `review-fleet:v1` **in single-lens reports too** — it is the name of the format,
not of the producer. Who produced it is in `lenses_ran`.

| Key | Value | What `bazel-post-report` does with it |
|---|---|---|
| `repo` | `owner/name` | Confirms it is publishing to the right repo. |
| `pr` | a number, or `none` | The target PR. `none` → the publisher takes the PR from Bazel's header line; without one, it stops and says so. |
| `base` | the base branch name | On the record; goes into the review body. |
| `head_sha` | 40 hex, full | Compared against the PR's current HEAD. Different → no inline anchoring. |
| `scope_cmd` | the command, one line | Goes into the review body, and proves the scope was resolved. |
| `files` | integer | `0` is a resolution failure → **the publisher refuses to post**. |
| `lenses_ran` | names separated by `, ` | Goes in the body. An all-clear with a lens missing claims coverage that never happened. |
| `lenses_skipped` | `none`, or `<lens> (<reason>)` separated by `, ` | An honest record of what was not looked at. |
| `verdict` | from the vocabulary | Goes in the body, never in the `event`. |

`verdict` is the **lenses'** verdict over this diff, and it is written without any knowledge of
the PR — the fleet never calls GitHub. `bazel-post-report` may publish a softer one after dropping
the findings the team already settled, and it says both numbers when it does. The file is not
rewritten to match.

All nine keys are **mandatory and non-empty**, in this order. One missing, empty or out of
order is an invalid report: `bazel-post-report` stops and says which, instead of publishing half a
review.

Together, `scope_cmd`, `files` and `lenses_ran` are the report's record of **coverage** —
what was swept, how much of it, and by which lenses. There is no coverage section in the body;
this is where that lives.

## The title and summary block

Right after the header, separated by one blank line. **Exactly** one H1 and three lines, in
this order, with no blank line between them and no fourth line:

```markdown
# Review Fleet — PR #123 · Add transfer endpoint

**Verdict:** request_changes · 2 findings (1 critical, 1 minor) · 1 cut (−27 lines)
**Scope:** `git diff origin/develop...HEAD` — 12 files · base `develop` · head `a1b2c3d`
**Lenses:** senior-code-reviewer, exploit-digger, lazy-senior-dev
```

**H1** — `<Producer> — <target>`, with the producer written like this:

| Producer | H1 |
|---|---|
| the fleet | `# Review Fleet — …` |
| `senior-code-reviewer` | `# Senior Code Reviewer — …` |
| `exploit-digger` | `# Exploit Digger — …` |
| `lazy-senior-dev` | `# Lazy Senior Dev — …` |

And the target: `PR #<N> · <PR title>` when there is a PR, otherwise ``branch `<name>` ``.

**`**Verdict:**`** — the verdict, then the aggregates separated by ` · `:

- the finding count: `N findings (<n> critical, <n> major, <n> minor, <n> nit)`, in that
  order, **omitting the severities that are zero**. A single finding → `1 finding`, singular.
  Zero findings → just `no findings`, with no parentheses.
- the cut count, **omitted when there are no cuts**: `M cuts (−L lines)`, where the dash is a
  minus sign `−` (U+2212). `1 cut`, singular.

**`**Scope:**`** — the `scope_cmd` in backticks, ` — `, `N files`, then ` · base <base in
backticks> · head <short 7-char sha in backticks>`.

**`**Lenses:**`** — the `lenses_ran` verbatim. When `lenses_skipped` is not `none`, a
` (skipped: <value verbatim>)` at the end of the same line.

## A finding

An `###` heading with the title, the metadata comment on the **immediately following line**, a
blank line, then the prose up to the next heading. **That prose is published verbatim** as the
body of the inline comment — which is why the language rule applies here.

```markdown
### Transfer debits any account by id
<!-- finding severity=critical class=authz lenses=senior-code-reviewer+exploit-digger path=src/api/transfer.ts line=88 side=RIGHT confidence=9 ref=CWE-639 -->

**critical · authz** (senior-code-reviewer + exploit-digger)

Transfer reads `accountId` from the request body without checking ownership.

**Trigger:** `POST /api/transfer` with another user's `accountId` debits their account.

**Fix:** resolve the account from the session, or assert `account.ownerId === session.userId`
before debiting.
```

The title is a short sentence, no trailing period, no severity prefix, no emoji — the level
line right below carries the severity.

### Attributes

All on one line, `key=value` separated by spaces, in this order:

| Attribute | Required | Value |
|---|---|---|
| `severity` | yes | From the closed vocabulary. |
| `class` | yes | From the closed vocabulary. |
| `lenses` | yes | Lens names joined by `+`. Two lenses = convergence, and the level line shows it. |
| `path` | yes | Path relative to the repo root, or `-`. |
| `line` | yes | The line in the file **after** the change, or `-`. |
| `side` | yes | `RIGHT` (default) or `LEFT` for a removed line. |
| `start_line` | no | For a line range; comes with `line` and, if `LEFT`, with `start_side`. |
| `confidence` | no | Whatever the lens returned: `8`–`10` from `senior-code-reviewer`, `high`/`medium`/`low` from `exploit-digger`. |
| `lines_saved` | no | Integer. **Required** on every finding in the `## Cuts` section. |
| `ref` | no | CWE/OWASP ids, no spaces, several joined by `,` (`CWE-89,OWASP-A03`). The lenses emit it that way. |

No value contains a space, so no value is quoted. If you feel the urge to quote, the value is
wrong.

`path=-` and `line=-` **always travel together**: that is the finding that anchors to no line
at all (architectural, spread out), and the publisher moves those to the review body instead
of trying to anchor them. One without the other is invalid.

`confidence` and `ref` live **only** in the metadata. Do not write "Confidence: 9" or
"CWE-639" in the prose — `bazel-post-report` is what decides how to show that on the PR.

### The prose, and only it

Four blocks, in this order, and **no other label is allowed**:

| Block | Shape | Required | Where it comes from |
|---|---|---|---|
| Level | `**<severity> · <class>** (<lenses>)` | yes | the finding's own metadata |
| Description | no label | yes | `body` (senior, exploit) or `cut` (lazy) |
| Trigger | `**Trigger:**` | when the lens gave one | `trigger` (exploit) |
| Fix | `**Fix:**` | yes | `fix` (senior, exploit) or `replacement` (lazy) |

One or two sentences per block, separated by a blank line. No `**Impact:**`,
`**Why it matters:**`, `**Evidence:**`, `**Risk:**`, `**Context:**` or any label that looks
useful in the moment — the finding is short on purpose, and a new label is the most common way
two reports on the same diff end up looking different.

### The level line

The first line of every finding's prose, and the only place the severity is **visible**
without opening the metadata comment. It is assembled from that same metadata, so the two can
never disagree:

```
**critical · authz** (senior-code-reviewer + exploit-digger)
```

- `severity` and `class` verbatim from the attributes, separated by ` · `, the whole thing in
  bold.
- The lenses in parentheses, joined by ` + ` (with spaces — the metadata uses `+` without
  them). Two lenses means two independent lenses found it, and that is the convergence signal;
  the line is where a human reads it.
- In `## Cuts`, `lines_saved` joins the bold part, with a minus sign `−` (U+2212):

  ```
  **minor · reuse · −27 lines** (lazy-senior-dev)
  ```

This is the exact string `bazel-post-report` publishes as the header of the inline comment, so the
prose goes to the PR verbatim with nothing assembled at publish time.

### Order within a section

In `## Findings`: by `severity` (`critical` → `major` → `minor` → `nit`), and within it in the
order the lens returned them. In `## Cuts`: by descending `lines_saved` **only** — a `major` cut
of 25 lines goes after a `minor` one of 40. Never change a `severity` or a `lines_saved` to make
an order fit.

## The sections

Three divisions, in this order, and no more. **An empty section leaves the file** rather than
sitting there saying "none" — and a section that is not in this table does not exist.

| Order | Section | Marker | Content | Destination on the PR |
|---|---|---|---|---|
| 1 | `## Findings` | — | findings with `<!-- finding … -->` | inline comments |
| 2 | `## Cuts` | — | findings with `lines_saved`, class from the Subtraction group | inline comments |
| 3 | `## Needs human verification` | `<!-- needs-human -->` | bullets | the review body — **never** becomes a finding |

They are the three divisions of the review: **what is wrong** (`Findings`), **what is surplus**
(`Cuts`), **what I could not settle on my own** (`Needs human verification`).

The marker goes on the line right below the `##`, followed by a blank line. `## Findings` and
`## Cuts` carry no marker — the `<!-- finding … -->` comments inside them already identify
everything.

**Do not create a fourth section.** Not for `exploit-digger`'s `trust_boundaries`, not for its
`checked_ok` coverage, not for `lazy-senior-dev`'s `out-of-scope` items, and not for a
"Summary", "Notes" or "Recommendations":

- `trust_boundaries` and `checked_ok` are sweep context, not findings. They belong in the
  run's working notes and do not enter the report. The file records what the
  review *found*; the header already records what it *covered*, through `scope_cmd`, `files`
  and `lenses_ran`.
- `out-of-scope` is a finding like any other: it goes in `## Findings` with
  `class=out-of-scope`, in a standalone `lazy-senior-dev` report. In the fleet it is discarded
  during the merge and never reaches the file.

### Who may emit what

| Section | fleet | `senior-code-reviewer` | `exploit-digger` | `lazy-senior-dev` |
|---|---|---|---|---|
| Findings | yes | yes | yes | `class=out-of-scope` only |
| Cuts | if `lazy-senior-dev` ran | — | — | yes |
| Needs human verification | if `exploit-digger` ran | — | yes | — |

A lens never writes another lens's section. If `senior-code-reviewer` ran alone and found
nothing, the file is header + title + summary and nothing else — that is a legitimate result,
and the `**Verdict:**` line with `no findings` already says so.

### Bullet format

`## Needs human verification` — one bullet per item, with `to_settle` on an indented line. No
per-item metadata, and **never** a `<!-- finding -->`:

```markdown
- `src/lib/webhook.ts:24` — the webhook signature is compared with `===`, but the provider's
  header casing is unconfirmed.
  **To settle:** check the provider's docs; if it is a shared secret, switch to a
  constant-time comparison.
```

## Language

**The file's content is in English** — titles, findings, cuts, verdict. This holds even when
the user's request came in another language: this file is the source of what goes to the PR,
it is read by the team and it stays in the history. Translating at publish time is rework and
a failure point; the file is born publishable.

## A complete example

```markdown
<!-- review-fleet:v1
repo: klever/app
pr: 123
base: develop
head_sha: a1b2c3d4e5f67890abcdef1234567890abcdef12
scope_cmd: git diff origin/develop...HEAD
files: 12
lenses_ran: senior-code-reviewer, exploit-digger, lazy-senior-dev
lenses_skipped: none
verdict: request_changes
-->

# Review Fleet — PR #123 · Add transfer endpoint

**Verdict:** request_changes · 2 findings (1 critical, 1 minor) · 1 cut (−27 lines)
**Scope:** `git diff origin/develop...HEAD` — 12 files · base `develop` · head `a1b2c3d`
**Lenses:** senior-code-reviewer, exploit-digger, lazy-senior-dev

## Findings

### Transfer debits any account by id
<!-- finding severity=critical class=authz lenses=senior-code-reviewer+exploit-digger path=src/api/transfer.ts line=88 side=RIGHT confidence=9 ref=CWE-639 -->

**critical · authz** (senior-code-reviewer + exploit-digger)

Transfer reads `accountId` from the request body without checking ownership.

**Trigger:** `POST /api/transfer` with another user's `accountId` debits their account.

**Fix:** resolve the account from the session, or assert `account.ownerId === session.userId`
before debiting.

### Settlement job has no test for the double-run case
<!-- finding severity=minor class=test-gap lenses=senior-code-reviewer path=src/jobs/settle.test.ts line=14 side=RIGHT confidence=8 -->

**minor · test-gap** (senior-code-reviewer)

The suite covers the happy path only; a second run on the same day is never exercised.

**Fix:** add a case that invokes `settle()` twice for one date and asserts a single ledger
entry.

## Cuts

### Hand-rolled retry duplicates the client's built-in backoff
<!-- finding severity=minor class=reuse lenses=lazy-senior-dev path=src/lib/retry.ts line=12 side=RIGHT lines_saved=27 -->

**minor · reuse · −27 lines** (lazy-senior-dev)

`retryWithBackoff` reimplements what `httpClient` already does via `retry: 3`.

**Fix:** delete the helper and pass `retry: 3` at the call site.

## Needs human verification
<!-- needs-human -->

- `src/jobs/settle.ts:40` — the cron cadence assumes settlement never runs twice for the same
  day.
  **To settle:** confirm with whoever owns the scheduler.
```
